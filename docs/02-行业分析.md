# 连锁餐饮巡店与运营改进 · 行业分析

课程作业资料整理｜公开资料归纳，未标注处的具体数字需二次核实

# 一、行业背景

连锁餐饮的门店数量增长快于管理人员增长，总部对门店的管控主要依靠督导巡店。门店越多、督导越少，“巡店—整改—复查”这条链路就越依赖标准化工具。近年来食品安全监管持续收紧，明厨亮灶、进货查验、温度记录等要求被写入日常检查项，门店需要留存可追溯的证据。

与此同时，多数连锁品牌已经上线巡店系统、培训平台和门店档案三套系统，但三者权限独立、状态割裂，总部很难拉出一张覆盖全链路的视图。这正是本项目访谈中平台工程师确认的情况（f30、f31）。

# 二、行业共性痛点

| 痛点 | 表现 | 对本项目的影响 |
|---|---|---|
| 判罚口径不一致 | 不同督导对同一问题定级不同，门店只收到扣分不知道如何改 | 同一问题反复出现，复发率居高不下 |
| 报告整理耗时 | 每份巡店报告需要人工整理 30—40 分钟 | 督导大量时间花在案头工作，现场巡店时间被压缩 |
| 整改证据链缺失 | 培训签到被当作“已学会”，整改照片被当作“已复查” | 问题看似闭环，实际未整改，风险后移 |
| 多系统数据割裂 | 巡店系统、培训平台、门店档案版本不一致，门店改名后历史问题断链 | 无法按门店、按问题连续追溯，样本可信度低 |
| 指标口径各说各话 | 总部看整改时限、门店看执行成本、督导看复查通过 | 同一件事拆成多次“成功”，比例失真 |

# 三、同类产品与技术实践

国外以“数字化巡检 + 合规留痕”为主，代表产品有 Checkit、Zenput（已并入 Crunchtime）、ComplianceMate，核心能力是把纸质检查表搬到移动端，配合拍照、温控设备读数自动采集，形成可审计记录。这类产品解决的是“记录标准化”，对问题归类与整改建议的智能化介入有限。

国内以餐饮 SaaS 与视觉巡检为主，美团餐饮系统、客如云、天财商龙等提供门店巡店、任务派发与数据看板；海康、商汤等提供后厨视频分析与明厨亮灶方案。它们的优势在硬件与视频流，弱项在“问题 → 整改动作 → 能力验证”的业务闭环。

大模型的能力边界决定了本项目的可行形态：多模态模型可以把照片、温度记录、培训演练材料结构化成字段，也能基于规则库给出归类建议和话术；但它无法承担现场处置、专业签核与复查结论。这与行业里“AI 出建议、人做决定”的普遍做法一致。

# 四、技术条件与差异点

| 维度 | 行业常见做法 | 本项目方案 |
|---|---|---|
| 数据接入 | 整套系统替换或深度改造 | 只读接口 + 带时间戳快照兜底，不替换现有系统 |
| 问题定级 | 人工按经验定级 | AI 出严重度建议，人工签核后生效 |
| 整改闭环 | 以照片上传作为完成 | 照片只触发复查，复查必须现场执行 |
| 培训效果 | 以签到率衡量 | 签到不等于学会，能力未验证即转人工 |
| 指标口径 | 各岗自报 | 各岗完成时间分开记录，固定分母与排除规则 |

# 五、风险与合规

个人信息与影像：巡店照片涉及员工与后厨画面，只有授权岗位可查看，评价记录暂留 90 天（f41、f43）。

越权风险：不得借用他人账号，最终决定与对外承诺须由对应审批人确认（f41）。

模型误判：低置信、资料缺失、版本冲突、系统不可用四类情形必须转人工，并标注触发原因、接手人与确认时间（f44）。

不可逆动作：扣罚、发布合格结论属于明确禁区，AI 不参与（f05、f52）。

# 六、结论

行业实践已经证明“巡检数字化”可行，但真正影响复发率与闭环时效的，不是通知发得多不多，而是归类口径是否统一、交接是否有接手人确认、复查是否有独立证据。因此本项目把切入点收敛到“问题归类建议 + 培训建议”，先做历史资料回放，再进入 10 店并行试点，暂不做自动扣罚与自动化结论发布。
