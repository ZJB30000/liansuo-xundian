# 连锁巡店与运营改进 · my-tool

面向连锁餐饮的巡店制度问答与整改建议助手（课程《FDE 工程技术与创新实践》二期项目）。

项目源自六岗位访谈与 36 条事实：AI 负责证据结构化、问题归类建议、制度问答与整改单草稿；
**定级、复查与处置仍由人工完成**（HITL：Human-in-the-loop）。

> 边界红线：不自动扣罚、不自动发布合格结论、不用整改照片代替复查、不自动定级。

本 README 即仓库主入口：包含项目背景、系统架构、智能体设计、安全设计、测试与质量、
部署与演示、全部交付物索引（docs/01~16）与提示词 1~10 交付对照表。

---

## 1. 项目背景与业务问题

连锁餐饮门店的巡店检查目前高度依赖人工：督导到店纸质打分、拍照留证、回办公室手工录入、
微信群催整改、月底 Excel 汇总。六岗位（运营总监、督导、店长、食安、培训、协调员）访谈
共沉淀 **36 条事实**，其中反复出现的问题有三类：

| 问题 | 事实来源 | 现状影响 |
| --- | --- | --- |
| 制度查询慢 | 督导现场遇到问题要翻 Word 制度库 | 一份制度平均翻找 10 分钟以上 |
| 整改闭环靠催 | 店长签收后无人跟进，复查靠记忆 | 问题复发率约 34%，整改闭环约 10 天 |
| 证据难追溯 | 照片散落个人手机、记录事后补 | 月底汇总口径不一，食安证据难留存 |

项目的目标（均为目标值，不作为合同承诺）：问题复发率 34% → 15%，整改闭环 10 天 → 5 天，
10 店试点归类一致率 ≥ 95%，重大问题漏报为零。

**AI 的位置**被刻意限制在「结构化、建议、台账」三个环节；「现场处置、专业签核、复查结论」
三个环节保留给人。这既是安全设计，也是与访谈中各岗位的顾虑一一对应的结果——
店长不接受 AI 直接定责，食安不接受照片代替复查，运营总监只要可追溯的台账。

## 2. 功能总览

系统包含三大功能块，全部经过真机验证：

### 2.1 巡店制度问答（RAG）

- 制度文档切片后建立 **FAISS 向量索引 + BM25 关键词索引**，双路检索经 **RRF 融合**排序；
- 回答为 **SSE 流式输出**，底部附引用来源（文档名、片段预览、融合得分），可追溯；
- 向量接口不可用（限流/断网）时**自动降级为 BM25**，问答不中断；
- 大模型调用失败时**降级为固定流程问答**，不抛 500。

### 2.2 智能体（Agent 模式）

- 自研 **Harness 循环**：模型决策 → 工具执行 → 结果回填 → 再决策，最多 5 轮熔断；
- **六个工具** Function Calling：检索制度（search_policy）、查巡检记录
  （get_store_record）、问题归类建议（classify_issue）、证据校验（validate_evidence）、
  建整改单草稿（create_rectification_draft）、提交人工审核（submit_for_review），
  模型自主决定调用顺序；
- 建单前**强制人工确认**（HITL）：模型只能产出草稿预览并挂起，员工点「确认建单」后
  才真正创建——确认使用**一次性令牌（10 分钟有效）**，且只能由发起人本人确认；
- 证据校验门禁：**无有效一次性证据令牌一律拒绝建单**，杜绝凭空编造巡店事实。

### 2.3 管理后台（仅管理员）

- `/admin/kb`：制度知识库上传与管理（版本变化自动重建索引）；
- `/admin/prompts`：系统提示词模板维护（**版本化**，改完立即生效）；
- `/admin/audit`：对话审计——命中「规避检查」等违规关键词的消息**自动标红**，
  管理员可复核全部会话历史。

## 3. 系统架构

五层分层架构，源码在 `src/my_tool/`，与 `tests/` 一一对应：

```text
api/       接口层：登录鉴权(JWT)、/api/chat(SSE+限流)、HITL 确认、
           知识库/提示词/审计管理、SSR 后台页
agents/    智能体编排层：Harness 循环、LLM 网关（流式/供应商可配置）、六工具
services/  服务层：制度知识库（切片 + FAISS/BM25 混合检索）
core/      规则层：归类建议与校验（规则版本化、置信度阈值、转人工）+ 提示词注入防护
utils/     通用校验工具
```

请求主链路：登录签发 JWT → 提问（并发限流检查）→ 注入检测 → 混合检索 →
构造提示词（管理员模板 + 输出格式红线）→ 流式生成 → 落库与审计 → 引用来源回传。
智能体链路在此基础上换为 Harness 循环，事件流（工具调用、确认请求、最终回答）
原样透传给前端。

## 4. 安全设计

| 机制 | 实现 | 验证方式 |
| --- | --- | --- |
| 登录鉴权 | JWT，全部业务接口整组依赖登录态 | 未登录访问返回 401（P-03 用例） |
| 角色隔离 | 员工/管理员 RBAC，管理页仅管理员 | 员工访问 /admin/* 返回 403（P-01 用例） |
| 同账号并发限流 | 上限 2 条回答，超出返回 429 与中文提示 | B-07 用例（含真实缺陷修复，见 §7） |
| 提示词注入防护 | 4 类注入模式检测 + 防御声明注入 | 对抗用例 A-01~A-10，拦截类 100% |
| HITL 确认 | 建单前挂起，一次性令牌 10 分钟 | N-04 真机全链路验证 |
| 证据门禁 | 无有效证据令牌拒绝建单 | tests/test_agent_tools.py |
| 对话审计 | 违规关键词标红 + 管理员复核 | tests/test_admin.py |

四条边界红线贯穿所有文档与代码：**不自动扣罚、不自动发布合格结论、
不用整改照片代替复查、不自动定级。**

## 5. 测试与质量

三层测试体系，从单元到真机：

1. **单元/集成测试**：`pytest` 共 **105 项**，与 src 五层结构对应，离线可跑；
2. **真机评测**：30 条评测用例（巡店口径），glm-4-flash 真机基线 **22/30**，
   运行器 `scripts/run_eval.py`，报告见 [docs/eval_report.md](docs/eval_report.md)；
3. **场景化测试**：**38 条量化用例**（正常 8 / 边界 8 / 对抗 10 / 权限 6 / 故障 6），
   全部真机执行并形成 5 份可视化测试文档（docs/10~14），含截图与过程记录。

**一个真实的缺陷故事（B-07）**：并发测试中发现，知识库未就绪（503）的失败请求
在获取限流额度后未归还，导致后续所有请求永久 429。定位为「acquire 之后、流开始之前
的初始化失败路径泄漏额度」，修复为 try/except 先归还再抛错，105 项测试回归通过后
真机复测通过。「发现 → 修复 → 回归 → 复测」全过程记录在
[docs/11-边界场景测试.docx](docs/11-边界场景测试.docx)。

通过门槛：正常类 100%，边界类 0 个 500，对抗类拦截 100% + 诱导类 ≥ 80%，
权限类 100%，故障类 100% 中文提示。

## 11. 常见问题（FAQ）

**Q1：为什么 AI 不直接给出处罚结论？**
六岗位访谈里这是店长与食安岗共同的顾虑：处罚依据必须经人核实，AI 只能看到文本与照片
描述，看不到现场。所以系统把 AI 限制在「建议」位，定级与处置由人工签核，且建议结果
绑定规则版本号，事后可按当时版本重建——升版不删旧版，历史结论永远可追溯。

**Q2：智能体会不会「自由发挥」乱建单？**
三重约束：第一，Harness 循环最多 5 轮，防止无限发散；第二，建单工具前有证据校验门禁，
没有有效的一次性证据令牌直接拒绝；第三，就算模型产出了草稿，也必须经过 HITL 挂起，
员工点「确认建单」才真正创建。三条约束分别有对应单元测试与真机用例。

**Q3：检索为什么要 FAISS + BM25 两路？**
制度文档里有大量编号与术语（如「冷藏柜温度 0~4℃」「f21」），纯向量检索对精确编号
召回不稳，纯关键词检索又理解不了同义表述。两路检索用 RRF 融合排序后互补；
向量接口被限流时 BM25 单独兜底，这也是真机实测出现过的情况（F 类用例）。

**Q4：同一员工连发两条提问为什么第二条会 429？**
同账号并发限流上限 2 条回答。SSE 是长连接，排队等待会积压，所以直接拒绝并给出中文
提示，让用户等前一条生成完。限流额度在流结束（含异常、断连）时归还；B-07 缺陷正是
失败路径漏归还导致的，修复过程见 §5。

**Q5：确认令牌为什么 10 分钟就过期？**
建单草稿里的温度、时间等证据有时效性。挂起超过 10 分钟，门店现场情况可能已变化，
继续确认会产出失真单据。过期后重新发起即可，令牌一次性使用且只能本人确认。

**Q6：管理员改了提示词模板，重启服务才生效吗？**
不用。模板存数据库并版本化（`kb_store.py`，旧版本停用但留痕可回溯），`/admin/prompts`
保存后下一次提问立即生效，管理员可随时回滚到历史版本。

## 12. 术语表

| 术语 | 含义 |
| --- | --- |
| RAG | 检索增强生成：先从制度库检索相关片段，再让大模型基于片段作答，减少编造 |
| FAISS | 向量相似度检索库，用于语义召回 |
| BM25 | 经典关键词检索算法，对编号/术语等精确匹配强 |
| RRF | 倒数排名融合：把两路检索的排名融合为一个综合排序 |
| SSE | 服务器推送事件：回答逐字流式输出到网页的技术 |
| HITL | 人在回路：AI 产出草稿、人做最终决策的协作模式 |
| Harness 循环 | 智能体主循环：模型决策→工具执行→结果回填→再决策，带轮次上限 |
| Function Calling | 大模型按预定义工具规范自主发起调用的机制 |
| JWT | JSON Web Token，登录态凭证 |
| RBAC | 基于角色的访问控制：员工/管理员权限隔离 |
| fXX | 业务挖掘报告中的事实编号，全部文档统一引用 |
| HITL 确认令牌 | 建单确认的一次性凭证，10 分钟有效，仅发起人可用 |

## 13. 关键设计决策（十问定案摘要）

| 问题 | 结论 | 架构影响 |
| --- | --- | --- |
| Q1 执行方式 | 人工到店拍照 | 无 IoT/视频层，架构轻 |
| Q2 检查表 | 统一模板 | 写死+版本字段，不做配置界面 |
| Q3 规模 | 100~500 店 | 单体应用+对象存储即可 |
| Q4 AI 定位 ★ | 只建议不决策 | 置信度路由转人工 |
| Q5 部署 ★ | 公有云 | 直接调大模型 API，成本最低 |
| Q6 整改闭环 | 系统内闭环 | 轻量状态机+定时器（超时升级） |
| Q7 终端 | 企微 H5 | 免安装+SSO，开发量小 |
| Q8 弱网 | 离线补传 | 本地缓存+同步队列+冲突规则 |
| Q9 权限 | 分级可见 | RBAC+数据范围+组织树 |
| Q10 证据 | 留存≥1年可审计 | 不可变存储+审计日志 |

完整论证见 [docs/06-需求定义文档.docx](docs/06-需求定义文档.docx) 与
